# @AuraEnabled and ConnectApi

> Part of `reviewing-apex` — see SKILL.md for the always-on Quick Reference and routing.

> **Cross-domain boundary.** This file defines the Apex side of the Apex→LWC contract. If you are also building the LWC component that calls these methods, load `reviewing-lwc` for the component-side rules.

- Narrow inputs and outputs. Use typed wrapper classes — not raw JSON strings — for structured LWC responses.
- **In a namespaced package, never return a raw `SObject`/`List<SObject>` whose custom fields the LWC reads.** Once the package namespace is applied at version-creation time, custom fields and relationships serialize under their real API names — `ns__Foo__c` / `ns__Foo__r` — so a component written against an unnamespaced dev org reads `undefined`: no exception, no console message, and `.filter()`/`.map()` chains collapse into dead UI. Require a typed `@AuraEnabled` DTO with unprefixed, lowercase property names so the wire contract is identical in both orgs. Standard fields (`Id`, `Name`, `CreatedDate`) carry no prefix and are the only safe direct reads. LWC-side tell: any `record.Foo__c` in JS where `record` came from an `@AuraEnabled` call. Note the asymmetry with `@salesforce/schema` module ids, which must **not** carry the namespace — do not "fix" one rule by applying the other.
  ```apex
  // BAD  @AuraEnabled public static List<Bundle_Item__c> listItems(Id parentId)  → item.TemplateName__c is undefined
  // GOOD @AuraEnabled public static List<BundleItemSummary> listItems(Id parentId) → item.templateName
  ```
- **Inbound types must be concretely deserializable.** Every `@AuraEnabled` method *parameter* — and every `@AuraEnabled` field on a wrapper passed **in** — must be a concrete Apex type the framework can rebuild from client JSON. An untyped `Object`, `Map<String, Object>`, or `List<Object>` used as an inbound parameter (or as a field of an inbound wrapper) fails deserialization at the LWC→Apex boundary with `Apex Type unsupported in JSON: Object`; the argument then silently arrives `null`, surfacing downstream as a confusing "required field is missing" error rather than a type error. The restriction is **directional** — those same untyped shapes are fine as *return* types (Apex→LWC). Flag any inbound `Object`/`Map<String,Object>`/`List<Object>` and require concrete types (e.g. `Map<String, String>`), resolving richer or strongly-typed values server-side instead of round-tripping them through the client (which also avoids lossy string conversion of date/number/boolean fields).
  - **Test blind spot:** an Apex test that constructs the wrapper in Apex never crosses the JSON boundary, so it passes while the real component call fails. When reviewing such a method, confirm the inbound wire shape is exercised by the Jest/integration call — a green Apex test class does not prove the contract.
- `cacheable=true` only when the method performs no DML, callouts, cart/checkout mutations, or session-specific side effects.
- Catch exceptions and rethrow as `AuraHandledException` with a user-friendly, sanitized message. Never expose internal detail.
- Isolate `ConnectApi` calls behind a wrapper/service to keep controllers thin and give tests a stable seam.
- **Do not let an LWC directly trigger a state-changing external callout through an `@AuraEnabled` method.** State-changing external operations must originate from a verified internal event — a DML trigger, a Platform Event consumer, or a Flow — so the mutation is tied to a server-side state change rather than an arbitrary client request. (The classic CSRF vector is different: state-changing **GET** handlers — `@HttpGet` Apex REST methods and Visualforce page-load actions — which must stay read-only. `@AuraEnabled` itself runs over POST with framework CSRF tokens.)
- Enforce CRUD/FLS (`WITH USER_MODE`) on every `@AuraEnabled` method, and keep the enclosing class `with sharing`. On Experience Cloud, never return PII or account data to a guest context.
- **A new entry-point class with no `classAccesses` grant is inert for every non-admin.** A user can invoke an `@AuraEnabled` method only when their profile or an assigned permission set grants access to the Apex class — adding the class and granting access to it are separate metadata acts. The class compiles, deploys, and works perfectly for the admin who built it, then every entry point fails for the target persona and the feature renders empty with no useful message. **No Apex test, Jest test, or `deploy validate` catches this.** Flag any new class exposing an entry point to a non-admin persona (`@AuraEnabled`, `@InvocableMethod`, `@RestResource`, `@RemoteAction`, a Visualforce controller) that does not appear in the `classAccesses` of a permission set shipped in the same changeset. Review the permission-set diff alongside the class diff, check how sibling classes in the same folder are granted, and require the grant to ship as metadata rather than as a manual post-deployment step. Skip only where the repo demonstrably does not gate Apex access per permission set.
- **A Named Credential callout also needs External Credential principal access.** The running user needs a permission set granting the External Credential principal (`externalCredentialPrincipalAccesses`); without it the callout fails within a second although both credentials exist. Ship that grant with the entry point, like `classAccesses`. A post-install script runs as an install user with no permission sets, so callouts from `onInstall` are unproven. The token a Named Credential mints never reaches Apex, so no design can hand it to browser code or another service.
- **Removing or renaming an `@AuraEnabled` method breaks every open tab once.** Tabs keep the old LWC bundle until a reload, so their calls fail with "No apex action available" after the deploy or package upgrade. Keep the old method for a release (delegating to the new one), or say so in the release notes.
- **Every `@AuraEnabled` getter on a response DTO ships.** A getter returning the full SObject serializes the whole record for every row, even when the plain fields were trimmed. When sizing a payload, read the getters, not just the fields.
- **An exception escaping the method rolls back the whole transaction.** A message like "record created, but adding its items failed" is therefore false: nothing was created. Word it as a full failure, or use partial-success DML (`Database.insert(records, false)`) when part of the work must survive.
- **An Aura request over 4 MB fails opaquely**: the LWC sees `status 500, body {}` inside an HTTP 200, with the real error buried in an `aura:systemError`. Never send file bytes as a base64 parameter; upload through the platform file upload, pass the `ContentDocument` Id, and size-guard on the client.
